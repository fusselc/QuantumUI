# 07_UX_SPEC.md

## Purpose

This document specifies the interaction model, user flows, states, and content rules for QuantumUI. It translates the principles in `04_DESIGN.md` into concrete, testable UX behavior. `08_GUI_SPEC.md` covers the corresponding visual and component specification.

## Primary User Flows

### Flow 1: First Experiment (Beginner)

1. Onboarding screen states plainly what QuantumUI does and that everything starts private and on a simulator.
2. User picks a template (for example, "See superposition happen").
3. Guided prompt box shows the template's editable natural-language description and inline suggestions.
4. User submits; system shows a generation-in-progress state with a plain-language label ("Turning your idea into a quantum circuit...").
5. Result screen shows: generated code, circuit visualization, a "Run on simulator" primary action, and a beginner-level explanation of what the experiment will show.
6. After execution, results appear alongside the explanation, with a clear Simulator label and a "Try changing something" prompt.
7. User is offered "Save privately" (default, no action required beyond normal save) and separate optional actions: export notebook, connect GitHub, share to dataset, share socially.

### Flow 2: Editing Generated Code (Intermediate/Advanced)

1. From any result screen, user selects "Edit code."
2. Editor opens with the generated Qiskit code, syntax highlighting, and a persistent "Generated by AI — edited by you" label once a change is made.
3. User can re-validate before running; validation errors appear inline, in plain language, with a technical detail toggle.
4. Re-running always defaults back to simulator unless the user re-confirms hardware execution.

### Flow 3: Hardware Execution Confirmation

1. User selects a hardware backend from a clearly separated "Real quantum hardware" section, distinct from simulator options.
2. A confirmation step displays: backend name, provider, shot count, estimated queue/cost information if available, and a one-sentence reminder that real devices are noisy.
3. User must take a distinct confirming action (not the same button used for simulator runs).
4. Job status view shows queued/running/complete/failed states with plain-language descriptions, not just raw provider status codes.

### Flow 4: Sharing an Experiment

1. From a saved experiment, user opens "Share this experiment."
2. Four independent toggles are shown, each defaulting to off: Repository, Public dataset, Social post, Research/arXiv package.
3. Selecting any toggle opens a preview of exactly what will be shared (fields, license if applicable, destination) before a final confirm action.
4. No toggle enables another; each requires its own confirmation.

### Flow 5: Notebook Export

1. User selects "Export" from a saved experiment.
2. Choice between "Download Jupyter notebook" and "Open in Google Colab."
3. Exported notebook includes code, circuit, configuration, and a comment block explaining provenance; it never includes credentials.

## Interaction States

Every experiment must expose a visible state from this set: **Draft, Validating, Ready to run, Running (Simulator), Running (Hardware), Complete, Failed, Cancelled**. State changes must be announced to assistive technology, not conveyed by color alone, consistent with WCAG guidance that information must not depend on color perception alone. [web:120]

## Error and Recovery UX

- Validation errors: plain-language summary first, technical detail available on demand, and a suggested next action (edit, regenerate, or pick a simpler template).
- Execution failures: state what failed (for example, "The quantum provider could not run this job") without exposing raw provider stack traces by default.
- Network/timeout errors: offer retry with the same idempotent request rather than silently resubmitting a duplicate hardware job.

## Accessibility and Interaction Requirements

- All primary actions must be reachable and operable via keyboard alone, with visible focus indicators meeting WCAG 2.2's Focus Appearance guidance (adequate size and contrast between focused and unfocused states). [web:120][web:128]
- Interactive targets (buttons, toggles, small icons) must meet at least the WCAG 2.2 minimum target size guidance, and be spaced to avoid accidental activation. [web:120][web:95]
- Any drag-based interaction (for example, reordering saved experiments) must have a non-drag alternative, per WCAG 2.2 guidance on dragging movements. [web:120]
- Destructive or hardware-triggering actions must not fire on press-down; they must only trigger on release, reducing accidental activation. [web:120]
- Authentication for account or provider connection must offer at least one method that does not rely solely on remembering a password (for example, a password manager-compatible flow or passkey). [web:120]

## Content and Tone Rules

- Use second person and active voice: "You generated this circuit," not "A circuit was generated."
- Never use the word "proof" or "confirmed" for a single simulator or low-shot hardware run; prefer "this result suggests."
- Every technical term introduced in a beginner-level explanation must have an inline, dismissible definition available on first use.
- Error messages must avoid blame ("Something went wrong" is acceptable; "You made a mistake" is not).
