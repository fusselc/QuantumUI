# 04_DESIGN.md

## Design Thesis

QuantumUI should make quantum computing feel like a guided lab, not a code editor with a chatbot attached. It must reduce intimidation without hiding the actual work: every plain-language request resolves into visible Qiskit, a circuit, an execution plan, results, and an explanation of uncertainty.

The interface has two equal obligations: help beginners act confidently and help advanced users verify, change, and export everything. Simplicity means progressive disclosure, not removed capability.

## Core Principles

### Show the Chain of Evidence

Every experiment follows a visible chain: **question → generated plan → Qiskit and circuit → validation → execution configuration → result → interpretation → saved record**. A user can inspect any stage, and each stage should identify whether it was generated by AI, supplied by a template, or edited by the user.

### Safe Defaults, Deliberate Escalation

Start with a simulator, conservative shot defaults, and curated templates. Moving to real hardware, publishing a repository record, entering a dataset, or creating a social post requires a separate affirmative choice with understandable consequences.

### Teach Without Pretending

Use plain language first, define technical terms on demand, and distinguish fact, estimate, and AI interpretation. Never frame a noisy hardware result as proof of a scientific claim. Explain what the run supports, what it cannot establish, and what a user could try next.

### Preserve Agency and Portability

Users own their work. They can read and edit the Qiskit, choose an AI-provider path, choose a compute backend, export notebooks, and keep experiments private. No core learning workflow may depend on a single LLM, hardware provider, or cloud notebook service.

### Make Complexity Navigable

Expose information in layers:

- **Explore:** template cards, examples, and a guided prompt.
- **Understand:** circuit visualization and plain-language explanation.
- **Inspect:** generated code, validations, parameters, and execution details.
- **Advance:** editable code, provider configuration, notebooks, GitHub, and reproducibility assets.

## Experience Model

The primary workspace centers on an experiment canvas with three persistent concepts: *what I asked*, *what will run*, and *what happened*. The UI should never bury the current execution state or data-sharing state. Clear labels must show Simulator/Hardware, Draft/Validated/Running/Complete/Failed, Private/Public, and Generated/User-edited.

Circuit visuals should be a teaching surface, not decoration: gates have readable names, measurement is visually distinct, and each visualization has a text alternative. Qiskit supports circuit and job-data visualizations, so QuantumUI should preserve enough structured information to render them consistently rather than relying only on screenshots. [web:90]

## Visual Language

Use a calm, high-contrast scientific-lab aesthetic: generous spacing, clear hierarchy, direct labels, and purposeful motion only for state changes. Color can reinforce meaning but never be the sole indicator; pair it with labels, icons, patterns, and accessible text. Controls must be keyboard-operable, touch-friendly, and visibly focused in line with WCAG 2.2 guidance. [web:84][web:88]

Avoid sci-fi clichés, unexplained Bloch-sphere imagery, and dense mathematical notation as default decoration. Visuals earn their place only when they clarify the experiment.

## Trust Moments

The product must create intentional pause points:

- **Before execution:** show code validation, backend, simulator/hardware status, shots, and an estimated provider constraint when available.
- **Before hardware execution:** require confirmation and state that real devices can be noisy and queued.
- **Before GitHub/public sharing:** preview exactly what will be committed or published.
- **Before dataset sharing:** show data fields, license, destination, and an opt-in confirmation.
- **After results:** show raw output alongside an explanation, confidence/limitations, and next-step options.

## Content Style

Write with curiosity and precision. Prefer “This result suggests…” over “This proves…,” “Try this next” over “You should know…,” and “The AI generated this draft” over “The answer is…”. Avoid jargon unless it is defined in context. Never use language that implies the user is unintelligent for being new to quantum computing.

## Design Constraints

- The baseline experience must be usable without an LLM API key, hardware account, GitHub account, or public-data consent.
- Generated code must never be visually hidden behind a paid or advanced-only mode.
- Security warnings must be clear and calm; never display or echo credentials.
- The UI must not present pathways for cryptographic attack, offensive cybersecurity, or key breaking.
