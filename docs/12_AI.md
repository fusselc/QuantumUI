# 12_AI.md

## Purpose

This document defines how QuantumUI turns natural language into Qiskit code and plain-language explanations, and the rules that keep this process transparent, swappable, and safe.

## Design Principles

- **The AI proposes; the user disposes.** Every generated artifact is a draft that the user can inspect, edit, reject, or regenerate before it runs.
- **No vendor lock-in.** The Generation Service must work with a self-hosted/open-source model or a hosted API key, selected by the user, through one common interface.
- **Explainability over authority.** Explanations describe what the AI did and how confident it should be, not present output as ground truth.

## Generation Pipeline

1. **Intent parsing:** Interpret the natural-language request, template selection, and any prior conversation context into a structured experiment intent (objective, qubit count, gates of interest, desired backend type).
2. **Code drafting:** Generate Qiskit code and a circuit description matching the intent, using a model adapter (open-source/self-hosted or hosted API).
3. **Self-check pass:** The model or a secondary validation step reviews the draft for obvious errors, unsafe patterns, or requests outside scope.
4. **Static validation handoff:** Draft code passes to the Validation Service (defined in `06_ARCHITECTURE.md`) for syntax, dependency, and policy screening before being shown as ready to run.
5. **Explanation drafting:** After execution, a second generation pass produces a plain-language interpretation of the result, distinguishing simulator idealization from hardware noise.

This staged approach mirrors established agentic patterns, where an LLM decides on an action, a tool executes it, and results are returned for further reasoning rather than a single unchecked generation step. [web:115][web:113]

## Model Adapter Interface

A model adapter must implement:

- `generate_code(intent, context) -> draft_code, draft_explanation, confidence_notes`
- `explain_result(execution_record) -> explanation_by_level`
- `health_check() -> status`

Adapters are interchangeable. The product ships with at least one open-source/self-hostable adapter and support for common hosted-API adapters (for example, OpenAI- or Anthropic-compatible APIs), consistent with how QuantumUI must never require one specific LLM vendor.

## Prompting and Context Rules

- Include only the minimal context needed: current intent, relevant template, and prior turns in the same experiment thread.
- Never include another user's private experiment data in a prompt.
- Never include API keys, tokens, or credentials in any prompt sent to a model, including self-hosted ones.
- System instructions must explicitly state the safety boundary: no cryptographic attack, key-breaking, or offensive-security code generation, with a redirection to an educational, non-actionable explanation instead.

## Confidence and Uncertainty

Every generated draft carries a confidence signal derived from validation results (did it compile, did it pass static checks, did a self-check flag issues). Explanations must state, in plain language, whether a result reflects an idealized simulation or a real noisy device, and must avoid words like "proves" or "confirms" for single small-sample runs.

## Evaluation

Before and after releases, sample generated experiments should be evaluated for:

- Syntactic and semantic validity of Qiskit code
- Circuit correctness relative to stated intent
- Successful execution rate on simulators
- Policy compliance (no unsafe content generated)
- Human-reviewed explanation quality and beginner clarity

Community benchmarking efforts for Qiskit code generation already exist as a reference point (for example, HumanEval-style benchmarks adapted to Qiskit), and QuantumUI's own evaluation suite should track similar dimensions over time. [web:72]

## Human-in-the-Loop Requirements

- Code execution, especially on hardware, always requires explicit user approval — never fully autonomous execution.
- Any AI-drafted explanation destined for public/dataset/social use must go through the same consent and review path defined in `COMMUNITY.md` before publication.
- Users can always request a plain explanation of why the AI produced a given result.
